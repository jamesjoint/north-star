Architecture Approaches

Three ways to evolve the job search app into a multi-user product

A

Minimal footprint — SQLite + bolt-on auth

Keep the existing Express + SQLite stack. Add user tables, scope existing tables to users, add magic link auth with a lightweight library (e.g. Lucia or better-auth). Migrate SQLite to Turso (cloud-native SQLite, zero schema changes needed).

Pros

  • Least rewrite — existing queries mostly unchanged
  • Fast to ship
  • Low complexity

Cons

  • Turso is another vendor dependency
  • SQLite has limited concurrency for shared job scoring jobs
  • Feels "bolted on" as scale grows
B

Full-stack upgrade — PostgreSQL + custom auth ⭐ Recommended

Migrate from SQLite to PostgreSQL (on Railway or Supabase). Add better-auth for magic link auth. Redesign the data model cleanly for multi-tenancy: shared jobs table, per-user scores, boards, and tracker_entries.

Pros

  • Clean multi-tenant data model
  • Postgres handles concurrent scoring jobs well
  • Own everything — no lock-in
  • Standard stack, easy to reason about

Cons

  • More upfront work — schema migration, query updates
  • Slightly longer to first working version
C

Backend-as-a-service — Supabase

Replace the database and auth layer with Supabase (managed Postgres + built-in magic link auth + row-level security). Keep Express for the API and scraping logic, but let Supabase handle auth, user management, and DB hosting.

Pros

  • Magic links work out-of-the-box
  • Row-level security enforces user data isolation automatically
  • Dashboard for DB inspection is handy

Cons

  • Supabase vendor lock-in
  • Free tier has pausing behavior that's annoying for invite-only apps
  • Mixes two auth systems (Express sessions + Supabase JWTs)
